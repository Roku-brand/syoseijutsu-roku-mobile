# UI統一・パーソナライズ変更：負荷と通信量のレポート

作成日：2026年10月15日（日本時間）

今回の構成では、カード数に比例して画像通信やAPI呼び出しが増えることを避けています。「探す」の初回表示は画像分が約111KiB増えます。一方、マイページの既存背景を軽量化した効果が大きく、マイページの初回画像取得量は約1.37MiBから約123KiBへ減りました。蔵書・マイ処世術はフォルダーを開くまで個別カードを描画せず、開いた後も20件ずつ表示します。

## 実装内容

- 設定の「アプリ設定」と、その中の「ホーム画面に追加」を削除。
- 対人術・仕事術・人生術・心理学・行動科学・戦略論・組織／経営論・古典／思想・実践知の9分野は、人気ランキングと同じ画像を利用。新たに生成した画像は組み込んでいない。
- 探すではボタン背景、マイページでは履歴・蔵書のカード左端に配置。特集はその記事固有の表紙を使う。
- マイページのタブを緑・青・朱色に整理。閲覧履歴を処世術・理論・特集へ分割し、特集の閲覧も端末内に記録。
- 蔵書・マイ処世術の最初の表示はフォルダーカード。既存フォルダー・保存先・旧理論IDを維持。フォルダー削除では内容を未整理へ戻す。

## 測定条件

同一PCのChromium、390×844px、各3回。変更前はmainの `b24dc8a` と同じソースのWeb書き出し、変更後は本変更のWeb書き出し。保存は処世術100件・理論100件・特集4件、履歴100件、マイ処世術300件のダミーデータを使用した。旧IDはアプリの通常の復元処理で正規化される。

APIは同じ応答を返すテスト用fixtureで置換し、サービスワーカーを無効化した。PlaywrightのAPI interceptionではHTTPキャッシュも無効になるため、画像量はキャッシュなしの保守的な値。通信欄は画像のencodedBodySizeの合計であり、HTML・フォント・API・JSを含む総通信量ではない。JS欄のgzipはローカル圧縮サイズで、配信環境の圧縮設定による実通信量とは区別する。

## 比較結果

| 項目 | 変更前 | 変更後 | 意味 |
| --- | ---: | ---: | --- |
| 探すの初回画像 | 約63KiB | 約174KiB | 9分野の背景追加分が約111KiB |
| マイページ履歴の初回画像 | 約1,404KiB | 約123KiB | 巻物背景の軽量化により約91%減 |
| 蔵書タブのDOM要素数 | 1,638 | 230 | フォルダー前面化により約86%減 |
| マイ処世術タブのDOM要素数 | 1,709 | 229 | 300件を最初から描画しない |
| 履歴タブのDOM要素数 | 563 | 446 | 種類別・20件ずつの表示 |
| タブ5往復中の特集API追加取得 | 5回 | 0回 | 60秒以内は共通キャッシュを利用 |
| JS全体のgzipサイズ | 約1,145KiB | 約1,149KiB | 増加は約4KiB、約0.4% |

「探す」初回の累積CPUタスク時間（3回の中央値）は約379msから約691msへ増加した。画像の追加処理があるため、初回負荷の増加はゼロではない。タブ操作から2回目の描画フレームまでの計測（51操作）では中央値約24ms・95パーセンタイル約33msだった。これらはこのPC上の参考値で、端末や同時負荷によって変わり、ネットワークを含む画面表示時間や実機の応答時間を保証しない。

JavaScriptヒープはGCの時点で変動する。5往復後の観測範囲は変更前約20.5～42.4MiB、変更後約15.3～21.0MiBだった。これはJavaScriptのみであり、画像デコード・GPU・ネイティブ全体のメモリではない。今回の画像デコード用メモリの増加だけを、この値から推定することはできない。

## 重くしないための対策

1. 9分野は4つの軽量ファイルを共用する。理論6分野は同じ画像シートの別の領域を表示し、カードごとに別画像をダウンロードしない。
2. 追加した分野画像は合計113,378バイト。マイページ背景は1,373,416バイトから48,112バイトへ変更。特集カードにも小さな表紙画像を用意した。
3. フォルダー一覧では個別カードをマウントしない。中身は20件から始め、利用者が「もっと見る」を押した時だけ増やす。端末内の全データを20件へ削除する処理ではない。
4. フォルダーの件数は一度集計する。画像のために新しい外部APIやライブラリーを追加しない。
5. 特集データは60秒間の共通キャッシュと同時リクエストの共有を使う。期限が過ぎても自動ポーリングは行わず、次に対象画面を開いた時に更新する。CMSの公開・取り下げ・再試行は明示的な更新を行う。
6. 閲覧履歴は端末内のIDだけを保存する。特集履歴は最大100件で、本文や画像そのものを履歴に複製しない。フォルダー操作も既存の端末内保存を使う。

## 注意点・測定の限界

- 画像がなかった探す画面では、初回に約111KiBの増加がある。すべての画面・すべての利用者で通信が減るという意味ではない。
- 実際に開く特集の種類、CMSで指定された外部画像、フォント、端末のキャッシュによって通信量は変わる。
- 既存PWAはキャッシュを返しつつバックグラウンドでも再検証する。今回この方式は変更していないため、再表示の通信量が必ず0になるとは報告しない。
- 60秒以内の再表示では特集を再取得しないため、別端末の変更がすぐ反映されない場合がある。60秒経過後の再表示、またはページ再読み込みで更新する。表示中の自動ポーリングは行わない。
- ローカルCPU時間は同時負荷の影響を受けるため、応答速度の改善率の根拠にはしていない。上記と生データに参考値として記録している。
- iPhoneアプリは依頼どおりビルドしていない。Safari実機・ネイティブの描画速度、ピークメモリ、実回線での総消費量は未計測。今回の判定はWebの描画量・取得量と構造上の抑制策に基づく。
