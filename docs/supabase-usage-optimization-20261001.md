# Supabase 通信量の最適化（2026-10-01）

対象は `theory-rights-release` の `codex/maintenance-refactor-20261001`。前の保守性改善に追加したアプリ側の変更です。本番 DB・Edge Function・公開サイトへの適用は行っていません。

## 調査結果

本番プロジェクト `psfexomjhivqieehcrzx` の直近24時間の API Gateway ログをパス単位で集計しました。本文、アクセストークン、ユーザー個別の行は取得していません。

| --- | ---: |
| content_categories | 315 |

OPTIONS は上表に含めません。アプリ、管理画面、開発・検証からのアクセスを含むため、利用者数や1人当たりの通信量を表す値ではありません。Gateway ログには転送バイト数がないため、これだけで Egress 全体の内訳は断定できません。

旧実装では、起動・認証状態の変化・権限確認後に公開カタログを強制再取得し、同時呼び出しを統合していませんでした。公開テーブルから完全版の本文も取得したうえで、購入者は同じ本文を Edge Function から再取得していました。完全版の保存済みデータは通信失敗時だけ利用していました。

`paid_content.payload` の JSON テキスト量は、処世術241件で573,682バイト、理論617件で294,506バイト、学習14件で20,490バイト、計888,678バイトでした。これはレスポンスの外枠や HTTP 圧縮を含まない計測です。

## 実装

- 公開カタログは、無料の本文と完全版の一覧・配置情報を別の列指定で取得。完全版の処世術はタイトル・本文・実践文、理論は本文・出典を公開同期で取り直さず、認証済みの同期で取得します。
- 公開カタログに1時間の永続キャッシュを追加。再起動・権限確認・画面復帰時に再利用し、同時取得を1つの Promise に統合します。失敗したテーブルを空の正規データとして保存しません。
- 公開同期を再適用する際、すでに解決した完全版の本文を保持し、最新の公開一覧・配置情報を適用します。公開用キャッシュへ完全版の本文を書き込みません。
- 完全版も、サーバーで利用権限を確認した後、同じユーザーの1時間以内の保存済みデータを再利用します。キャッシュは権限を付与しません。サインアウト中の遅い読み込み・通信応答で完全版が復活しないよう世代番号を確認します。
- 完全版の同期は全種類の取得完了を確認してから成功・保存と判定。処世術本文の取得失敗には待機・再読み込み表示を用意します。30秒を超える取得は HTTP リクエスト自体も中断します。
- 閲覧は同じコンテンツ・同じUTC日に1回、保存は同じコンテンツで24時間に1回へ送信を抑制。サーバーの既存ルールと同じです。同時送信をまとめ、失敗した送信は次の操作で再試行可能です。この抑制はアプリを開いている間のメモリー内で働きます。
- 人気ランキングに30分の永続キャッシュを追加。公開操作は無効化して取得し直し、端末への保存も更新します。トレンド取得は件数ごとのキャッシュと同時取得の統合を行います。

## 効果の見積もりと更新間隔

本番の公開中完全版レコードについて、列を絞る前後に相当する JSON の量を SQL で集計しました。

| 完全版の部分 | 一覧情報 | 取得しなくなる本文等 |
| --- | ---: | ---: |
| 処世術 | 64,590バイト | 484,419バイト |
| 理論 | 166,228バイト | 131,363バイト |
| 合計 | 230,818バイト | 615,782バイト |

この部分は846,600→230,818バイト、約73%の削減見積もりです。無料データ・HTTP ヘッダー・圧縮・管理画面の取得は含みません。Supabase の請求対象 Egress 全体が73%減るという意味ではありません。キャッシュが有効な間の通常の再読み込みでは、カタログ・完全版本文の再転送も省けます。権限確認の通信は継続します。

通常の取得では、公開カタログ・完全版は取得後1時間、ランキングは30分までキャッシュを利用します。期限を過ぎた次の取得で更新するため、この期間と画面を開き直すタイミングに応じて変更反映が遅れます。公開カタログ・権限は起動、画面復帰、1時間ごとのチェックで更新します。古いキャッシュを読み込んだ後も画面を開き続ける場合、カタログの古さは次の定期チェックまで最大約2時間になることがあります。開いたままのランキングは次にその画面を開くときに確認します。オーナーの公開操作は強制取得して即時反映します。通信失敗時の既存の完全版キャッシュ利用も、利用権限をサーバーで確認できた場合に限ります。

版番号や ETag による差分配信、公開データの静的配信は、さらに節約できる候補です。今回は DB・Edge Function の更新を必要としないキャッシュと取得列削減を採用しました。利用状況が増えた場合は、実測に基づいて次の段階を検討できます。

公式資料: [Egress の扱いと削減方法](https://supabase.com/docs/guides/platform/manage-your-usage/egress)、[Storage の最適化](https://supabase.com/docs/guides/storage/production/scaling)。既に消費した使用量は減らず、新版を公開した後の消費が対象です。

OneDrive 配下の既存の Expo ファイル解決問題を避け、同じソースと依存関係を同期領域外へコピーして Web 検証しました。本番向け通信はダミー接続先とモックで代替しています。iOS・Android 実機、および公開後の実 Egress 削減率は未検証です。

## 運用

個人メモの保存キーは変更していません。キャッシュだけを調査する際も端末の保存領域全体を消去しないでください。

| 用途 | 保存キー | 通常の有効期間 |
| --- | --- | --- |
| 公開カタログ | `@shoseijutsu-roku/published-content/v1` | 1時間 |
| 完全版本文 | `@shoseijutsu-roku/paid-content/v11` | 1時間、ユーザー一致・権限確認が必要 |
| 人気ランキング | `@shoseijutsu-roku/popular-rankings/v1` | 30分 |
| トレンド | `@shoseijutsu-roku/trending/v2/<取得件数>` | 30分 |

リリース後は[組織の Usage](https://supabase.com/dashboard/org/vpjkpgxlpjulhwoqzxtt/usage)で同程度の利用期間を比較し、公開カタログの GET 回数・イベントの POST 回数も確認します。今回の最適化は取得列とクライアントキャッシュの変更であり、既存の DB ポリシーや API の権限設定を変更するものではありません。
