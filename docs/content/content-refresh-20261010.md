# DB本文更新と通信量の抑制

通常の本文修正はDBの公開行を更新するだけで反映する。今回の変更はその再取得の仕組みを改善するプログラム変更であり、一度Webへ公開する。

- 利用中は10分ごとに`content_revision`の1行・更新番号1つだけを確認する。変更がない場合、本文の再取得や完全版Edge Function呼び出しを行わない。
- 前面への復帰とWeb/PWAの接続復帰でも番号を確認する。確認は60秒以内の重複を抑制し、同時リクエストを共有する。
- バックグラウンド中の定期確認を行わない。Realtimeや常時接続は追加しない。
- 公開本文・人物像・分類・学習データの変更はDBトリガーで更新番号へ反映する。下書きのみ、同じ内容の保存、タイムスタンプだけの変更では番号を進めない。
- 本文取得に失敗した場合、更新番号を反映済みとして記録しない。完全版の本文と保存済みキャッシュを保持し、次回に再試行する。サインアウト後の遅延応答は適用しない。

本番に適用したマイグレーション履歴は`20261010052424_content_revision`。更新番号は公開可能な整数のみで、一般ユーザーは参照だけできる。更新用トリガー関数は既存の非公開`private`スキーマへ配置し、anon/authenticatedの実行権限を付与していない。

## 検証

- SQLの検証はトランザクション内で実行し、全変更をロールバックした。公開本文・取り下げ・理論・人物像・分類・学習データの変更検出、下書き／タイムスタンプ更新の除外、クライアントの書き込み禁止を確認。
- 実DBの更新番号SELECTは主キー参照で1行だけを取得。確認時の実行計画は共有バッファ2ページ、Execution Time 0.027ms。これは測定時のDB内処理時間で、HTTP通信時間や実際の料金を示す値ではない。
- 単体テストで確認の間引き、同時確認の共有、通信失敗後の再試行、完全版キャッシュの保持、サインアウト後の応答破棄を確認。
- ブラウザで無料版・完全版の変更反映、変更なしの場合の本文通信0回、接続復帰、バックグラウンド中の定期通信0回、短時間の復帰確認の抑制を確認。

起動時の既存のカタログ取得と認証・利用権確認は引き続き行う。初回オフライン起動の同梱データや静的SEOページの更新は、通常のDB本文修正とは別にWebビルドが必要。
